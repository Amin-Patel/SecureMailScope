## 3. Findings

### F7 — Non-email TLS captures produce a maximum-severity "email security" verdict — Critical [executed]

This is the benign false-positive measurement the brief asked for, and it is the
single most damaging behaviour in the tool. Running the pipeline over the benign,
**non-email** TLS captures in the NonTor set:

| Capture | Email packets | Score | Level / Grade | Findings |
|---|---|---|---|---|
| `browsing.pcap` | 0 | 100 | CRITICAL / F | 1,978 (1,369 `CERT_EXPIRED`, 588 `CERT_UNTRUSTED_CA`) |
| `browsing_ger.pcap` | 0 | 100 | CRITICAL / F | 851 |
| `browsing_ara2.pcap` | 0 | 100 | CRITICAL / F | 546 |
| `browsing2.pcap` | 0 | 100 | CRITICAL / F | 229 |
| `facebookchat.pcap` | 0 | 100 | CRITICAL / F | ~140 |
| `Hangouts_voice_Workstation.pcap` | 0 | 100 | CRITICAL / F | ~160 |
| `Skype_Audio.pcap` | 0 | 55 | CRITICAL / F | 4 |
| `hangout_chat`, `hangoutschat`, `icqchat`, `ICQ_Chat` | 0 | 100 | CRITICAL / F | — |

Every one of these has **zero email packets** (`summary.total_packets == 0`,
`protocols_detected == []`), yet the tool reports a maximum-severity assessment
of the "email infrastructure." The cert/TLS checks run over *all* TLS in the
capture regardless of port, and there is no gate that says "no email traffic was
found, so there is nothing to assess." A judge who uploads any web-browsing
capture is told their email posture is CRITICAL.

The immediate drivers are F8 (now()-based expiry/trust) and F9 (TLS-1.0
mislabel), but the structural defect is separate: **the security engine never
scopes its TLS/cert findings to email sessions.** Fix: only run the TLS/cert/PKI
checks on streams whose server or client port is an email port (or that were
reached via a detected STARTTLS upgrade), and short-circuit to an explicit "no
analyzable email traffic" result when none exist (the functionality map's empty
state #24 already specifies this message).

Contrast: the clean captures behaved correctly — `aimchat`, `skypechat`,
`skype_chat`, `AIM_Chat` all scored 0/LOW/A. So the FP is specific to captures
that contain *any* TLS.

### F8 — Certificate expiry and trust are evaluated against `datetime.now()`, not capture time — Critical [executed]

`cert_analyzer.py:125` (`now = datetime.now(timezone.utc)` in
`_analyze_single_handshake_chain`) and `:249` (same in `_serialize_certificate`)
compare `not_after`/`not_before` against the wall clock at analysis time. A
forensic tool analyzes *historical* captures, so this is systematically wrong.

Measured on `Workstation_Thunderbird_POP.pcap`:

- First frame timestamp: `2015-07-13T19:14:13Z`.
- Leaf cert `smtp.googlemail.com`: valid `2015-02-18 → 2015-12-31`. **Valid at
  capture time.** Reported `CERT_EXPIRED`.
- Same for `*.googleapis.com`, `pop.googlemail.com`, and their `GeoTrust Global
  CA` / `Google Internet Authority G2` chain — all valid in July 2015, all
  flagged expired.

The same root cause corrupts `CERT_UNTRUSTED_CA`. The chain itself builds and
verifies (`presented 3, built 3`, signatures OK), but the terminal anchor
(`GeoTrust Global CA`) is not in today's `certifi` bundle — I confirmed
`GeoTrust Global CA in store: False` against the 121 roots certifi currently
ships. So a correctly-configured 2015 Google mail server is reported as *expired
and untrusted*. This invalidates "Certificate expiration analysis" and
"Certificate chain validation" on every historical capture.

Fix: thread the capture's own time (earliest frame, or per-frame time) through
`_evaluate_pki_rules` and compare validity against that. For trust, either state
plainly that trust is evaluated against the *current* Mozilla store (a
documented limitation) or pin/bundle a historical anchor set; do not present
"root not in my 2024 bundle" as a security finding about the server.

### F9 — TLS 1.3 sessions are reported as CRITICAL "TLS 1.0 Detected" — Critical [executed] (item 6, escalated)

`Bugs-Found-and-Fixed.md` item 6 records this as "silently harmless by luck."
It is not harmless. My controlled fixture `D_smtps465_tls13.pcap` contains a
**real TLS 1.3 handshake** (tshark confirms `TLSv1.3`, cipher
`TLS_AES_256_GCM_SHA384` `0x1302`). The pipeline reports:

- `summary.tls_versions = {'TLS 1.0': 1, 'TLS 1.2': 1}`
- Finding **`PROTO_TLS10_DEPRECATED`, CRITICAL**, "1 TLS handshakes using TLS 1.0"

Cause is exactly as item 6 described but never fixed at source:
`tshark_helper.py:106-118` maps the *record-layer* version. My tshark probe on
every NonTor capture shows ClientHello record-layer pinned at `0x0301` while the
handshake/supported-version is `0x0303`+. So the ClientHello is read as "TLS
1.0". This fabricates a CRITICAL finding on clean, modern TLS.

Worse, the two layers of the same JSON payload disagree: on
`Workstation_Thunderbird_POP.pcap` the rule engine's `summary.tls_versions`
reports `TLS 1.0: 28` while `ml_assessment.sessions[*].tls_version` reports the
`effective_tls_version`-corrected `TLS 1.2: 28` for the *same* sessions. The rule
engine and the report read the uncorrected value; only the ML block uses the
corrected one.

Fix: add the `supported_versions` extension field to
`extract_tls_handshakes()` (as item 6 already recommended) and prefer it, and
apply the correction to the version used by `check_tls10/11/ssl3` and the
summary, not just the ML feature extractor. Until then the deprecated-protocol
findings cannot be trusted on any capture containing a ClientHello.

### F10 — "STARTTLS negotiation detection and validation" is unimplemented; a successful upgrade is reported as cleartext CRITICAL — Critical [executed]

The problem statement lists "STARTTLS negotiation detection **and validation**"
as both an objective and a deliverable. Nothing in the code parses the STARTTLS
command/response sequence or the subsequent upgrade.

Measured on my fixture `A_smtp587_starttls.pcap` — a *correctly* configured
server: `EHLO` → advertises `STARTTLS` → client `STARTTLS` → `220 Ready to start
TLS` → real TLS 1.2 handshake. The tool reports:

- `PROTO_CLEARTEXT_DETECTED`, **CRITICAL**, "16 plaintext packets"
- session `encrypted: False`, plus a 30-point `encryption_penalty`
- final score 75 / CRITICAL / F

Same for `E_imap143_starttls.pcap` (IMAP STARTTLS). Root cause: `encrypted` is
decided purely by destination port at `pcap_analyzer.py:229`
(`protocol in ['SMTPS','IMAPS','POP3S']`); a port-25/143/587 stream that upgrades
via STARTTLS is never recognized as encrypted. The failure direction is worse
than a miss: it penalizes the *correct* configuration the spec wants rewarded.

Compounding it, `check_missing_starttls` (F27) gates on capture-wide
`has_any_tls = len(tls_handshakes) > 0`, so in a capture that has one TLS
session *and* one plaintext SMTP session the STARTTLS-missing finding never
fires. And `starttls_used` is hardcoded `False` at both ML call sites
(`ml_risk_service.py:53`, `dataset_builder.py:199`), which is why that feature's
importance is 0.0031 — it is never set true anywhere.

Fix: detect the STARTTLS command and its `220`/`a1 OK` response in the plaintext
prefix of a stream, mark the post-upgrade traffic encrypted, and emit a real
validation verdict (upgrade offered? accepted? completed? downgraded/stripped?).

### F11 — The ML layer cannot change any outcome, the anomaly detector never fires, and 99.21% is memorization — Critical [executed]

Four spec deliverables ride on this layer (risk classification, anomaly
detection, posture scoring, threat prioritization). Measured against the saved
`risk_classifier.joblib`:

- **The classifier is a strict distillation of `label_session`.** On 3,528
  synthetic rows it disagrees with the rule on only 30, and every disagreement
  is the model predicting a *lower* class than the rule.
- **On 9,719 novel realistic combinations** (random valid sessions with 0–4
  simultaneous cert/PKI problems — states the training set never contains, since
  it uses at most one PKI finding per row), the model disagreed with the rule on
  1,385, and **in every single case the model was equal-or-lower — never higher
  (`novel_model_higher_than_rule: 0`).**
- The fusion rule (`ml_risk_service.fuse_risk_level`) is *raise-only*. A model
  that is never higher than the rules therefore **can never change the fused
  risk level.** It is architecturally incapable of adding anything. On my one
  fixture where it *did* flip a level (`C_smtps2465_nonstd`, `ml_elevated: True`),
  the elevation was spurious — the deterministic engine had under-scored a
  session it failed to attribute to a port (F13), and the model "raised" it back;
  that is the model papering over a different bug, not catching a real risk.
- **The anomaly detector has never fired.** Across every capture I ran — 2,238
  ML-scored sessions total, including 0/1021 on `browsing.pcap`, 0/519 on
  `browsing_ger.pcap`, 0/48, 0/47 — `is_anomaly` was `False` every time. On the
  synthetic training distribution it spends its entire 0.08 contamination budget
  on the majority class (228/2418 CRITICAL flagged, **0/32 LOW, 0/80 MEDIUM**),
  i.e. it flags common risky sessions and never the rare ones an anomaly detector
  is for.
- **The 99.21% held-out accuracy in `training_report.txt` measures
  memorization.** Labels are a deterministic function of the features
  (`label_session`), so the "accuracy" is just "did the RandomForest reproduce a
  function we already have in code." A majority-class baseline on the real rows
  is 96.3% (F20). This number should not appear in a judging deck as a model
  quality metric.

Also note the model's label space is now a **strict subset** of the rule
engine: `label_session` has no branch for `email_authentication` or
`known_malicious_certificate` (added to `security_engine.py` on 09-19, after the
models were trained 09-17), so those finding types are invisible to the ML
layer. The feature *schema* itself is consistent — `clf.n_features_in_ == 24 ==
len(FEATURE_NAMES)` — so there is no schema-drift crash; the drift is semantic.

Fix options, in order of honesty: (a) present this as a **rule-distillation /
explainability** model and drop the accuracy claim and the "detects anomalies"
claim; or (b) if the AI/ML deliverables must be genuinely met, train on labels
that are *not* a function of the same features (e.g. hand-labeled real captures,
or an anomaly baseline built only from known-good `secure_enterprise`-style
traffic) so the model can disagree with the rules in a useful direction.

### F12 — Unbounded duplicate `CERT_EXPIRED` findings; A–F grade discriminates nothing — High [executed]

`browsing.pcap` produced **1,369 `CERT_EXPIRED` + 588 `CERT_UNTRUSTED_CA`**
findings (1,978 total). The dedup key at `security_engine.py:439` is
`(rule_id, subject, frame)`, so the same cert re-presented across many frames
yields a new finding each time. "Prioritized security findings" becomes an
unreadable wall. And because `finding_score` is `min(round(raw), 100)`, any
capture with a handful of cert findings pins at 100/F: **every real capture I ran
graded F.** The A–F grade therefore carries no information across real inputs.
(Fixing F8 removes most of these, but the dedup/cap issue remains independently:
dedup per unique certificate, not per frame, and cap the per-rule contribution.)

### F13 — Non-standard implicit-TLS ports are invisible to protocol/session detection — High [executed]

The statement names IMAPS/POP3S/SMTPS explicitly, which includes non-standard
deployments. My fixture `C_smtps2465_nonstd.pcap` (implicit TLS on port 2465)
produced `total_packets: 0`, `session_count: 0`, `protocols_detected: []`,
streams `{'TCP': 1}` — because 2465 is not in `EMAIL_PORTS`
(`pcap_analyzer.py:26`, `tshark_helper.py:17`). Yet the cert/TLS path still fired
findings on it, so the capture is simultaneously "no email sessions" and "3
findings" — an internally inconsistent result, and it fed the spurious ML
elevation in F11. Detection is purely a static port table; there is no
heuristic that says "this stream did a TLS handshake and carried SMTP/IMAP/POP3
verbs, so treat it as mail."

### F14 — CORS reflects any Origin with credentials, on every endpoint — High [executed]

`main.py:57-63` sets `allow_origins=["*"]`, `allow_credentials=True`,
`allow_methods=["*"]`, `allow_headers=["*"]`. Starlette reflects the caller's

### F15 — Path traversal in the delete endpoints — High [executed]

`_delete_single_analysis` (`main.py:246-260`) builds
`RESULTS_DIR / f"{capture_id}.json"` and then globs `UPLOAD_DIR.glob(f"{capture_id}.*")`
with no validation that `capture_id` is a bare identifier. Using a traversal
sequence as the `capture_id`, both `DELETE /api/analysis/{id}` and
`POST /api/analyses/delete-batch` deleted files I had placed **outside**
`results/`/`uploads/` (canary files confined to my scratchpad; each deleted file
was one I created for the test). The `.glob("{id}.*")` on the uploads side is
especially dangerous because a single request removes every sibling matching the
stem. Fix: reject any `capture_id` that is not `^[A-Za-z0-9_]+$`, and resolve the
final path and confirm it is inside the intended directory before unlinking.

The same unsanitized-identifier pattern reaches `reject_pending_knowledge_source`
(`DELETE /api/knowledge/pending/{finding_type}` →
`knowledge_ingestion.reject_pending` → `PENDING_DIR / f"{finding_type}.md"`).

### F16 — Path traversal in the results/report endpoints allows arbitrary `.json` read — High [executed]

`GET /api/analysis/{capture_id}/results` and `.../report` build
`RESULTS_DIR / f"{capture_id}.json"` from the raw path segment. A traversal
`capture_id` returned the contents of a `.json` file outside `results/` (I read

### F18 — Credential redaction is defeated by the stream viewer's hex toggle — High [executed]

Deliverable #3 (per `Teammate-Deliverables-3-and-4.md`) advertises "visible"
credential redaction. The redaction is applied only to the ASCII `payload`; the
same chunk keeps `hex_payload`, the **raw unredacted bytes**. Measured on
`test-data/smtp.pcap` and my `B_imap143_plain_login.pcap`: the `payload` reads
`[REDACTED_PASSWORD]`/`[REDACTED_PASSWORD_BASE64]`, but `hex_payload` decodes
back to the original credential line. `StreamViewerModal.jsx:351` renders
`chunk.hex_payload` verbatim when the user flips to "hex" view (button at
`:225`), and the raw bytes are also persisted in `results/{id}.json` and served
by `GET /.../stream/{id}`. So the secret a forensic reviewer was told is redacted
is one toggle away. Fix: redact in the hex representation too (or derive hex from
the redacted text), and don't persist raw credential bytes.

### F19 — RAG grounding is broken for the finding types that actually occur — High [executed]

The seed corpus has 12 docs, but the two types that dominate real output are
mis-wired:

- **`certificate_pki`** (every chain finding: `CERT_EXPIRED`, `CERT_UNTRUSTED_CA`,
  etc.). The offline `_fallback_explanation` (`gemini_service.py:182-224`)
  branches on `finding_type` and has **no branch** for `certificate_pki`, so all
  chain findings get the generic "deviate from NIST SP 800-52r2" boilerplate. On
  the flagship `legacy_ssl3` demo, that means 4 of 7 findings get boilerplate and
  `CERT_EXPIRED` comes back with `ai_reference: null`. Across all my runs,
  `CERT_EXPIRED` grounded 3/2979 and `CERT_INVALID_CHAIN_ORDER` 0/23.
- **The self-improving loop cannot close.** `knowledge_ingestion.FINDING_TYPES`
  still lists the *original 8* types and omits `certificate_pki` and
  `email_authentication` — which are exactly the two types recorded in
  `gaps.json`. `POST /api/knowledge/gaps/certificate_pki/propose` and
  `.../email_authentication/propose` both return **HTTP 404 "Unknown
  finding_type"** (executed). So every real gap is un-proposable; only
  `plaintext_protocol` (which needs a key) reaches the 503 path.

`RAG-Knowledge-Base-Design.md`'s premise — "a fixed, closed set of 8
`finding_type` values" — no longer matches the code (there are now ~11 emitted
types, and `certificate_pki` collapses nine `rule_id`s into one type). Fix: add
`certificate_pki`/`email_authentication` branches to the fallback and to
`FINDING_TYPES`, and key grounding off `rule_id` where the type is a catch-all.

### F20 — The "108 real sessions" are the validation captures, and each session's certificate is fabricated — High [executed]

Tracing `train.py`'s dataset build in memory (no model written): the 108 real
rows come entirely from the demo captures + the four NonTor email captures — the
**same files the docs cite as "verified against real captures."** So any
"validated on real data" claim is training-set evaluation. The genuinely
held-out benign set is the browsing/chat/voice captures — on which the tool
fails catastrophically (F7).

Worse, `extract_real_sessions`/`assess_sessions` apply `certificates[0]` and
`certificate_chains[0]['pki_findings']` to **every** ServerHello in the capture.
On `Workstation_Thunderbird_POP.pcap` that smears one cert across 28 sessions;
the 28 rows collapse to a **single unique feature vector**, all labelled HIGH.
So "108 real sessions" is really ~5 distinct real vectors (measured:
`real_unique_vectors: 5`), four of which weren't in the synthetic set. The
per-session certificate attribution is not real — certs are matched by
"first-in-list," not by stream/frame. Fix: match each ServerHello to the cert
chain in its own stream; report the real distinct-session count.

### F22 — Unmapped TLS-version codes leak as raw hex into output — Medium [executed]

### F23 — Parser failure returns HTTP 500 with raw tshark stderr; extractor error-handling is inconsistent — Medium [executed]

Uploading a truncated or non-capture `.pcap` returns **HTTP 500** with the raw
tshark message (e.g. `...appears to have been cut short...`, leaking the internal
`uploads\<id>.pcap` path). Four NonTor files (`Workstation_Thunderbird_Imap.pcap`,
`SSL_Browsing.pcap`, `ssl.pcap`, `spotify.pcap`) fail this way as
"damaged/cut-short." The functionality map (#23) calls for a graceful "parser
failure / no relevant traffic" state, not a 500. And the extractors disagree
with each other: `extract_tls_handshakes` **raises** on non-zero returncode,
while `extract_structured_tcp_streams` and `extract_raw_certificates` swallow all
exceptions and return `{}`/`[]` — so a real parse failure sometimes 500s and
sometimes silently yields empty results. Fix: validate the capture up front,
return a 422 with a clean message, and make the extractors handle errors
uniformly.

### F24 — Upload buffered fully in memory before the size check; frontend/backend limits disagree — Medium [executed/code-read]

## 5. Weaknesses in the requirements themselves

- **The user-supplied statement differs from the repo's second-hand copy.** The
  verbatim NTRO text says "STARTTLS negotiation detection **and validation**",
  "**Complete** TCP stream reconstruction", "Certificate **chain validation**",
  "reports in JSON, PDF, **and** HTML", and "dashboard for security
  **monitoring**". The paraphrase in `Competitive-Landscape-SIH26159.md` softens
  several of these. Judge against the verbatim text (done above). **F32:** commit
  the real statement.
- **"Blockchain" is only the theme tag.** The statement's title theme is
  "Blockchain & Cybersecurity," but the word *blockchain* appears **nowhere** in
  the objectives, deliverables, or description. No competitor repo implements it
  either. Treat it as NTRO's category label, not a requirement — but say so
  explicitly in the pitch so judges don't ask why there's no chain. Do **not**
  bolt on a token "evidence ledger" and call it blockchain.
- **SPF/DKIM/DMARC, RAG/Gemini, and the SSLBL feed are extras, not
  requirements.** None of the three appears in the statement. They are legitimate
  differentiators, but they must be labelled as supplementary and (for the two
  active ones) kept out of the passive-analysis claim. The passive SPF/DKIM/DMARC
  reading from the capture is fine and correctly scoped; the active DNS lookup and
  the SSLBL download are the ones to fence off (F26).
- **Synthetic data is explicitly allowed.** The statement's dataset line permits
  generating IMAPS/POP3S/SMTPS captures with any client/server. So using
  synthetic captures is **not** a flaw. The flaws are narrower and stand: the ML
  *labels* are distilled from the rules (F11), and neither the rule engine nor
  the anomaly detector has a measured benign false-positive rate — which I
  measured for them here (F7: ~100% on non-email TLS; F11: anomaly detector 0
  hits). The statement naming IMAPS/POP3S/SMTPS also means implicit-TLS ports
  993/995/465 must work as first-class citizens (they do on standard ports;
  non-standard ports don't — F13).
- **"Risk score" and "posture" are undefined by the statement.** The tool's
  0–100 weighting and A–F thresholds are a reasonable local definition, but they
  are uncalibrated: every real capture pins at 100/F (F12), so the scale conveys
  no gradation on real inputs. Define and defend the scale, or it reads as
  decorative.

## 6. Remediation order (ranked by what changes a judge's conclusion)

1. **F8 (capture-time expiry/trust) + F9 (TLS 1.3 label) + F7 (scope findings to
   email traffic).** These three together are why *every* real and benign
   capture returns CRITICAL/F. Fixing them is the difference between a tool that
   discriminates and one that cries wolf on everything. Highest leverage.
2. **F10 + F27 (STARTTLS detection & validation).** Verbatim spec language,
   currently inverted (penalizes correct config). A demo that flags a properly
   secured server as cleartext CRITICAL is a credibility loss in the room.
3. **F15 + F16 + F14 (path traversal + open CORS).** Unauthenticated arbitrary
   file read/delete reachable from any web origin. Cheap to fix (identifier
   allow-list + origin allow-list); catastrophic if a judge or teammate probes it.
4. **F11 + F20 (the AI/ML story).** Four deliverables ride on a layer that
   provably can't change an outcome and never detects an anomaly, validated on
   its own training captures with a memorization metric. Either reframe it
   honestly (distillation/explainability, drop the 99% and "anomaly" claims) or
   retrain on labels independent of the features. This is the biggest gap between
   what the docs claim and what the code does.
5. **F17 + F18 (leaked credentials + defeatable redaction).** A forensic/security
   tool that leaks a real credential in its own repo and whose redaction is one
   toggle away undermines the core value proposition.
6. **F12 + F21 + F22 (finding-flood, report/dashboard disagreement, hex
   versions).** These make the output look unfinished even after 1–5 are fixed.
7. **F19 (RAG grounding) + F13 (non-standard ports) + F23–F25 (parser/upload/
   watcher robustness).** Polish that a thorough judge will hit.
8. **F26, F28–F34.** Passive-claim hygiene, honesty of the progress UI, deps,
   stale artefacts, console encoding, committing the spec, bind address.

Hand these to `builder` in this order. F8/F9/F7/F10 are the ones that change the
demo from "flags everything" to "flags the right things," and F15/F16/F14 are the
ones that must not be live when anyone else touches the box.
